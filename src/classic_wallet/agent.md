# Agent notes for `src/classic_wallet`

This directory contains the older/simple wallet implementation for this crate. The project also has the newer BDK-backed wallet in `src/wallet`; this module is built as the `classic` binary and is re-exported from the library as `bitvmx_wallet::ClassicWallet`.

## Files

- `main.rs` — CLI entry point for the `classic` binary. Loads `ClassicWalletConfig`, initializes tracing, decides whether a Bitcoin RPC client is needed, constructs `ClassicWallet`, and dispatches CLI commands.
- `cli.rs` — `clap` command definitions for the classic CLI.
- `classic_wallet.rs` — core classic wallet implementation and tests.
- `config.rs` — `ClassicWalletConfig` with Bitcoin RPC, key-manager, key-storage, and wallet-storage settings.
- `errors.rs` — `ClassicWalletError` enum and conversions from dependent crates.
- `mod.rs` — module declarations and re-exports.
- `README.md` — user-facing usage notes for the classic wallet CLI.
- `tui.rs` — currently empty/placeholder.

## What the classic wallet does

`ClassicWallet` manages logical wallets by identifier. Each identifier maps to a Bitcoin public key in local storage; private keys live in the `key_manager`/`key_storage` backend.

It can:

- create wallets by deriving keys (`create_wallet`),
- import/export wallets from secret/private keys,
- import partial private keys and store the aggregated public key,
- manually register/remove/list UTXOs as named funding entries,
- build and sign spend transactions using `protocol_builder`,
- optionally broadcast transactions through `bitvmx_bitcoin_rpc`,
- track pending transfers until explicitly confirmed or reverted,
- merge multiple UTXOs into one output,
- mine and fund wallets on regtest through Bitcoin Core RPC helpers.

## Storage model

Storage keys are generated by the private `StoreKey` enum in `classic_wallet.rs`:

- `wallet/index` — next derivation index for `create_wallet`.
- `wallet/name/{identifier}` — logical wallet identifier to `PublicKey`.
- `wallet/{identifier}/funding/{funding_id}` — funding entry storing `(OutPoint, amount_sat)`.
- `wallet/{identifier}/transfers/{funding_id}` — pending transfer storing `(txid, change_vout, change_amount_sat)`.

A funding entry is not automatically synced from chain state. The classic wallet trusts its local storage and updates it only when callers add/remove funding or confirm/revert transfers.

## Transaction flow

- `fund_address` spends one registered funding entry.
  - It refuses to spend if a pending transfer exists for the same `(identifier, funding_id)`.
  - It creates one or more destination outputs, optionally as taproot outputs.
  - Any change is sent back to the source public key as a segwit output.
  - It stores the transaction as pending; with `auto_confirm = true`, it immediately updates local funding state.
- `confirm_transfer` removes the pending transfer and original funding entry, then re-adds change under the same `funding_id` when change is non-zero.
- `revert_transfer` only removes the pending marker; it does not touch chain state or attempt replacement.
- `merge_utxos` spends several funding entries, sends the total minus fee to one segwit key output, and marks all source funding entries as pending. Confirming removes those funding entries because merge pending records have zero change.

## CLI notes

Run the classic wallet with:

```sh
cargo run --bin classic -- [OPTIONS] <COMMAND>
```

The default config is `config/regtest.yaml`. Most commands initialize a Bitcoin RPC client; `btc-to-sat` does not.

## Important implementation assumptions

- Inputs are modeled as segwit key spends (`OutputType::segwit_key` and ECDSA signatures), even if wallet keys may be created with different key types.
- Regtest helper funding depends on a reachable Bitcoin Core node and the configured node wallet.
- Fees are passed as absolute sats, not fee rates.
- Amounts are stored and accepted as sats.
- Pending transfers are a local safety mechanism only; they do not prove mempool or chain confirmation.
- `list_funds` and `get_wallets` use storage-prefix scans, so storage key format changes are compatibility-sensitive.

## Tests

Most tests live at the bottom of `classic_wallet.rs`.

- Normal unit tests use temporary storage paths under `/tmp` and construct `ClassicWallet::new(config, false)` to avoid RPC.
- Integration-style regtest tests are marked `#[ignore]` and require bitcoind/RPC.
- Useful commands:

```sh
cargo test classic_wallet
cargo test -- --ignored
```
